# Agent Instructions

This project uses **bd** (beads) for issue tracking. Run `bd prime` for full workflow context.

> **Architecture in one line:** Issues live in a local Dolt database
> (`.beads/dolt/`); cross-machine sync uses `bd dolt push/pull` (a
> git-compatible protocol), stored under `refs/dolt/data` on your git
> remote — separate from `refs/heads/*` where your code lives.
> `.beads/issues.jsonl` is a passive export, not the wire protocol.
>
> See [sync-concepts](https://github.com/gastownhall/beads/blob/main/docs/core-concepts/sync-concepts.md)
> for the one-screen overview and anti-patterns (don't treat JSONL as the
> source of truth; don't `bd import` during normal operation; don't
> reach for third-party Dolt hosting before trying the default).

## Quick Reference

```bash
bd ready              # Find available work
bd show <id>          # View issue details
bd update <id> --claim  # Claim work atomically
bd close <id>         # Complete work
bd dolt push          # Push beads data to remote
```

## Non-Interactive Shell Commands

**ALWAYS use non-interactive flags** with file operations to avoid hanging on confirmation prompts.

Shell commands like `cp`, `mv`, and `rm` may be aliased to include `-i` (interactive) mode on some systems, causing the agent to hang indefinitely waiting for y/n input.

**Use these forms instead:**
```bash
# Force overwrite without prompting
cp -f source dest           # NOT: cp source dest
mv -f source dest           # NOT: mv source dest
rm -f file                  # NOT: rm file

# For recursive operations
rm -rf directory            # NOT: rm -r directory
cp -rf source dest          # NOT: cp -r source dest
```

**Other commands that may prompt:**
- `scp` - use `-o BatchMode=yes` for non-interactive
- `ssh` - use `-o BatchMode=yes` to fail instead of prompting
- `apt-get` - use `-y` flag
- `brew` - use `HOMEBREW_NO_AUTO_UPDATE=1` env var

## Beads Issue Tracker

### Rules

## Agent Context Profiles

The managed Beads block is task-tracking guidance, not permission to override repository, user, or orchestrator instructions.

- **Conservative (default)**: Use `bd` for task tracking. Do not run git commits, git pushes, or Dolt remote sync unless explicitly asked. At handoff, report changed files, validation, and suggested next commands.
- **Minimal**: Keep tool instruction files as pointers to `bd prime`; use the same conservative git policy unless active instructions say otherwise.
- **Team-maintainer**: Only when the repository explicitly opts in, agents may close beads, run quality gates, commit, and push as part of session close. A current "do not commit" or "do not push" instruction still wins.

## Session Completion

This protocol applies when ending a Beads implementation workflow. It is subordinate to explicit user, repository, and orchestrator instructions.

1. **File issues for remaining work** - Create beads for anything that needs follow-up
2. **Run quality gates** (if code changed) - Tests, linters, builds
3. **Update issue status** - Close finished work, update in-progress items
4. **Handle git/sync by active profile**:
   ```bash
   # Conservative/minimal/default: report status and proposed commands; wait for approval.
   git status

   # Team-maintainer opt-in only, unless current instructions forbid it:
   git pull --rebase
   git push
   git status
   ```
5. **Hand off** - Summarize changes, validation, issue status, and any blocked sync/commit/push step

**Critical rules:**
- Explicit user or orchestrator instructions override this Beads block.
- Do not commit or push without clear authority from the active profile or the current user request.
- If a required sync or push is blocked, stop and report the exact command and error.

## Build & Test

All Rust, in one Cargo workspace rooted here. Each demo runs natively or in the browser.
Everything goes through the Makefile; `make` alone lists the targets.

```bash
make check                  # before every commit: fmt-check, clippy -D warnings, tests
make slow                   # slow checks the READMEs quote (release build, a few minutes)
make run DEMO=sandpile      # a demo in a native window
make web DEMO=sandpile      # the same demo alone in the browser (trunk serve)
make serve                  # every demo plus an index page, at localhost:8080
make siblings               # before/after a Rust update: build+test David's other Rust projects
```

- `make site` (`site/build.sh`) builds every demo into `dist/<demo>/` and writes
  `dist/index.html` from `site/index.html`. A demo is any top-level directory with both
  `Cargo.toml` and `index.html`. Its link text is its page `<title>`, and its blurb is
  its Cargo `description`, so a new demo needs no edit to the site or the Makefile. Its
  card picture is drawn by `site/thumbs.js`, keyed by directory name (a demo without its
  own picture gets a generic one). The script also renders `HOW-IT-WORKS.md` into
  `dist/how-it-works.html` with `tools/mdpage` and copies `site/style.css` and
  `site/thumbs.js`. The site's look follows the demos' palette; see `site/style.css`.
  GitHub Pages lets browsers cache every file for 10 minutes, so the pages load those two
  by fingerprinted URLs (`?v=<cksum>`), and every demo page gets `site/stale-page.html`
  inserted after `<meta charset>`: it reloads once if the page's own `.js`/`.wasm` are gone
  (a page cached from before a deploy). The build fails if either step is missed.
  Every demo's `index.html` names `site/loading.mjs` as trunk's `data-initializer`, which
  turns "Loading…" into a percentage; trunk records the `.wasm`'s size before wasm-opt, so
  `build.sh` writes in the size of the file actually served.
- A new command worth repeating gets a Makefile target with a `## description`, so
  `make help` lists it.
- Use `--release` for anything but small grids: debug builds simulate far slower,
  in wasm even more so.
- Toolchain: stable rustc (1.100 as of 2026-11-15) with the `wasm32-unknown-unknown`
  target, and `trunk` 0.22 (`cargo install trunk --locked`). Rustc 1.95.0 stays installed
  as a fallback (`rustup default 1.95.0`). Before updating Rust again, check that David's
  other Rust projects still build and pass their tests: `../CPeMulator`, `../nscheme`
  and `../llm_wiki/src-tauri`.
- `trunk` downloads `wasm-bindgen` and `wasm-opt` on its first build.

## Architecture Overview

- `ca_core/`: the shared crate, package `ca_core`. Don't name it `core`, which clashes
  with Rust's built-in crate. It re-exports `eframe` and `egui`, so demos don't depend on
  them directly. What it holds:
  - `run(title, make_app)`: opens a native window, or starts in the page's
    `<canvas id="the_canvas_id">`.
  - `Grid<T>`, plus `line` (the cells between two points, for gap-free drag painting)
    and `moore_counts` (each cell's count of 8-neighbours in some state, with edges
    handled once; Life, Brian's Brain and Wireworld use it).
  - `GridView`: draws a grid as one texture. Its `GridResponse` gives `hovered`,
    `pressed` (every frame held, for painting), `clicked` (once per click), and
    `cell_rect`/`cell_size` for drawing markers over cells. Both directions of the
    mapping go through its `Layout` (square, or hex as offset bricks), defined as plain
    functions with round-trip tests; `Layout::image` builds the picture without a window.
    `HEX_NEIGHBOURS` is the six neighbour offsets in the hex layout's axial coordinates
    (the sandpile and the snowflakes use it).
  - `Playback`: Run, Pause, Step, Restart and a speed slider. Each frame,
    `take_restart()`, then `advance()` returns `Idle`, `Step` or `Run(speed)`.
  - `Pace`: turns steps per second into steps per frame, carrying the fraction.
    `generations_per_frame` caps the work per frame by world area, so big worlds slow
    down rather than freeze.
  - `Rng`: a small seeded generator for random fills.
  - `About`: the side panel rendering the demo's `README.md`.
  - `readout` (the label/value grid at the bottom of every panel, with its `pointer` row
    "under the pointer"), `speed_cap_note`, `grouped` (numbers as 1,234,567), `signed`
    (two places, a true minus sign, never "-0.00"), `mix` (a colour between two) and `NAVY`
    (the background): shared so the demos' panels look and read alike.
  - `plot`: a small chart in the panel (dots or lines, linear or log axes), for a demo
    that measures something as it runs; every demo's chart uses it.
  - `controls_panel`: the scrolling left panel each demo puts its controls in. It is a
    fixed 290 points wide, so rows must fit or wrap: use `horizontal_wrapped`, and put
    sliders on their own line (a slider doesn't wrap and would run past the edge).
  - `About` opens by default only on windows at least 1,400 points wide.
  - `PaintStroke`: turns `GridResponse::pressed` into solid lines of cells to paint.
- One directory per demo (`sandpile`, `life`, `elementary`, `langtons-ant`,
  `brians-brain`, `wireworld`, `cyclic`, `snowflakes`, `langtons-loops`, `lattice-gas`,
  `critters`, `forest-fire`, `traffic`, `aggregation`; and two that aren't automata,
  `reaction-diffusion`, a chemical model, and `mandelbrot`, a fractal), each a binary crate with an `index.html` for trunk:
  - `main.rs` holds the UI.
  - `sim.rs` holds the rule, kept free of UI code so it can be tested natively.
- The UI is egui/eframe 0.37, with the `glow` backend. In 0.37, `App::ui` takes a
  `&mut Ui` (not `update(ctx)`), and panels are `egui::Panel::left(id).show(ui, ..)`.
  `Ui::id` and `Id::new` are deprecated: use `ui.make_persistent_id(..)`. Code from
  memory or older examples uses the old API.

## Conventions & Patterns

- Keep the simulation in `sim.rs`, separate from the UI, and test its invariants there.
- Move code into `ca_core` only once a second demo needs it.
- `HOW-IT-WORKS.md` explains the architecture and quotes timings and `ca_core` APIs:
  update it when those change, or it drifts from the code.
- Every demo has a `README.md` for a reader who has never heard of the automaton: the
  rule, where the name comes from, its history (who, when, why it mattered, with
  citations), things to try in the demo, and further reading. `main.rs` passes it to
  `ca_core::About` with `include_str!`, so the same text is shown inside the app.
- Check facts and citations in a README before writing them; don't fill gaps from memory.
- README conventions, so the demos read alike: the rule; where the name comes from (one
  sentence, or a heading only if it needs explaining); History; Things to try, with bold
  leads; Further reading last, starting with "The Wikipedia article [...](...)." when there
  is one. Citations: authors, *title in italics*, journal spelled out in plain text, volume,
  pages (year), en dash for ranges, links labelled `doi:...` or `arXiv:...`. British
  spelling, "anticlockwise", "forever", commas in numbers from 1,000, control names in
  *italics*. Notes for editors (which file a table came from, commit hashes) go in `sim.rs`
  doc comments, not the README. A Further reading entry: authors, *title*, journal volume,
  pages (year), then a labelled link (`[doi:...](...)`, `[PDF](...)`); the title itself is
  not the link. Journals by their usual short name, without a subtitle ("Physica D").
- In the panel, a negative number takes a true minus sign (U+2212), and a value that
  rounds to zero shows as "0.00", never "-0.00".
- A demo that isn't a cellular automaton says so in its opening: "not a cellular
  automaton" (Mandelbrot, reaction-diffusion) or "isn't quite" (Langton's ant,
  aggregation). Its README row may start "Not a cellular automaton but ...:"; its Cargo
  description is then the row without that prefix.
- Never put a paragraph after a nested list inside a list item: the About panel's renderer
  draws it outside the bullet. Nor a line break inside a link's text (it loses the space).
- Mention another demo by name in prose ("the sandpile, another demo in this project"),
  without a link: the README also shows in the native app, where a relative link goes
  nowhere.
- Panel conventions (David chose them on 2026-11-16, where the older demos disagreed):
  - Paused at start, unless the opening is itself the show; then a comment says why.
  - Restart returns to the demo's opening with the current settings; a demo you draw on
    from scratch has a separate Clear. A note says what Restart (and Clear) does. Where
    the opening is random, Restart draws it afresh (a typed seed, where there is one, is
    for reproducing a world).
  - The readout at the bottom is `ca_core::readout`, lowercase singular labels, numbers
    through `grouped`, and its last row is `pointer` ("under the pointer"), not a tooltip.
  - `speed_cap_note` wherever the cap can bite. Presets are highlighted chips with the
    chosen one's note below (a drop-down only for long lists: Life's patterns,
    Wireworld's circuits). A section's strong heading
    on its own line; option chips in lowercase; the world/size block last before the
    readout; "World:" for a 2D world's size.
- The demos' order and groups on the index page are `site/order.txt` ("== Group" lines),
  and the root README's "### Group" tables must match them (`site/build.sh` checks).
- `.cargo/config.toml` turns on WebAssembly SIMD for the browser builds; the sandpile's
  16-bit Jacobi stage (`sandpile/src/jacobi.rs`) relies on it to be fast there.
- The sandpile has four sweeps: plain, symmetric octant, and two 16-bit Jacobi stages
  (on a quarter of a centred pile, and on a rectangle around any other pile). Any change
  to them must keep the equivalence tests in `sandpile/src/sim.rs` passing, including
  the randomized one. They compare each fast path with the plain sweep (`plain()`)
  exactly.
- Test a demo's simulation by behaviour with known answers where possible: famous
  patterns doing what they are known to do (the diehard dying at 130), hand traces of the
  first steps, or mathematical identities (Rule 90 against Pascal's triangle mod 2).
  Design patterns (Wireworld circuits) by simulating candidates, not from memory.
